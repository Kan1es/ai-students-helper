# Архитектура и распределение работы

REST API принимает снимки курсов и вопросы; PostgreSQL хранит материал, версии,
диалоги и задания. Worker выбирает доступный вопрос через `FOR UPDATE SKIP LOCKED`,
устанавливает lease и фиксирует попытку до обращения к провайдеру. HTTP-запрос не
держит транзакцию БД. Общий timeout ограничен `asyncio.wait_for`.

Если процесс завершается, вопрос снова становится доступен после lease. Token попытки
не позволяет прежнему обработчику записать ответ после передачи задания другому.
При смене активной версии во время генерации результат отбрасывается и вопрос ставится
в очередь заново. Число попыток ограничено. Ручной retry разрешён только после failed.

Импорт полного снимка и переключение активной версии проходят одной транзакцией.
Идентификатор фрагмента = SHA-256 от course/version/lesson/index. Тексты старых версий
остаются в БД, но active=false исключает их из поиска. Источники в ответе — серверные
снимки фрагментов, выбранных по проверенным ID модели. Ответ не содержит ссылок,
сгенерированных моделью: URL возвращаются только в структурированных источниках.

История предыдущих завершённых сообщений выбирается только из текущего диалога.
Текущий урок даёт небольшой бонус ранжированию, но не закрывает остальные уроки курса.
Короткое продолжение вроде «не понял» наследует предыдущую тему для поиска.
Рекомендации выбираются из действительно использованных уроков и содержат следующий
шаг; персональную диагностику знаний эта первая версия не выполняет.

API, worker и импорт используют один JSON-контракт; прямой зависимости от исходной
БД нет. Инструмент выгрузки можно развивать отдельно.

## Ограничения первой версии

SQLite — только одиночная локальная разработка: блокировки SKIP LOCKED там отсутствуют.
Для рабочей очереди требуется PostgreSQL. Срок lease должен превышать timeout провайдера
с запасом на поиск; это проверяется конфигурацией. Состояние очереди видно через статусы
сообщений; health проверяет соединение API с БД, а не активность worker.

Семантическая достоверность ответа не определяется по совпадению ID источника. Это
отдельная экспертная оценка. Живой вызов выбранной LLM не входит в подтверждённые проверки
пока провайдер не подключён. В режиме extractive никакой LLM не вызывается.
